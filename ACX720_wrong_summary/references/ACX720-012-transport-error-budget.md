# ACX720-012：累计五次串口坏帧后监测程序退出

- 日期/状态：2026-11-06；软件回归与实板自动恢复已验证，待用户确认新窗口画面。底层 F12 偶发缺字节仍未解决。
- 环境：ACX720-V3/xc7a100t，F12、UART 1 Mbps、160×120 RGB565，电脑运行姿态识别与微信通知。
- 现象：某次监测 142.36 秒内在 5.03、28.17、93.89、100.06、142.36 秒发生五次超时，其间持续收到正常帧。累计错误到五次后 Python 抛出异常并退出。不是五次连续断流。
- 根因：上层把累计统计计数当成致命故障预算：`if counts['transport_errors'] >= 5: raise`。一次成功取帧不会清零累计数，导致可恢复的偶发丢帧最终必然终止监测。旧恢复过程也没有清晰的掉线界面或串口重连路径。
- 独立测量：关闭模型、UI 与微信的纯取图观测 180.36 秒，259 帧 CRC 正确、21 次响应缺字节，坏帧载荷仅收到 37293～38336/38400 字节，TX 拒绝计数低八位为零。可确认传输本身存在故障；不能仅据此在板端、线路或 USB 驱动之间定责。
- 修复：累计数仅作统计；每次完整有效帧清零连续错误数，连续失败时重开串口并握手。坏帧清理残留再取下一帧。载荷停止到达超过 350 ms 时提前拒绝不完整帧，同时保留总超时和完整 CRC。断流时显示异常、清除未完成的人体时序证据，不向模型交旧帧，不新建微信报警；已锁存报警仍需用户确认。新增同一端口实例锁，重复启动不竞争串口。
- 验证：23 项测试通过，其中真实解析器和实际 app 主循环注入六次分散丢帧后仍继续采样、无虚假报警；另覆盖七次分散错误、连续错误重连、USB 异常、缺失字节诊断与载荷静默超时。实板长测结果见下方。
- 证据：`fall_detection/runs/live_20261106_223807/` 为原失败记录；`evidence/transport_recovery/probe.json`、`runs/transport_recovery_180s/`、`tests/test_transport_recovery.py` 为诊断及回归。没有重烧位流，也没有把延长超时当成修复。
- 限制：自动恢复修复监测退出问题，不修复物理数据丢失；实测时长不代表无限期可靠。串口恢复间隙仍可能影响事件检测延迟和漏检率。
